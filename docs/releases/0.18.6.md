# v0.18.6 — Task-Scoped Tool Authority

## Why

DEDAL already had security principles for least privilege, read/write separation, prompt-injection resistance, and high-impact confirmation. The missing layer was an executable distinction between a tool being technically available and a specific task being authorized to use that tool in a particular way.

## Added

- `evals/tool-authority/contract-v1.json`
- `scripts/validate_tool_authority_contract.py`
- Runtime Contracts CI execution for the new validator.
- Task-scoped capability-envelope rules in Security Engineering.
- External audit provenance for agent/MCP least-privilege patterns.

## Contract decisions

A valid consequential action is bounded by:

`authority source + tool + mode + resource scope + task intent + confirmation state when required`

The contract rejects:
- read authority silently escalating to write;
- untrusted tool/content/model output creating permission;
- intent or resource-scope drift;
- unconfirmed high-impact actions;
- conditionally trusted external MCP calls whose approved schema identity is not pinned/verified in the modeled case.

## Security boundary

Tool descriptions, schemas, and returned content are data unless independently authorized. A connected MCP/tool server cannot grant itself broader privileges through natural-language instructions.

Authorization should be enforced outside the model at the host/tool/service boundary when such a seam exists. The public Core contract does not itself intercept every native provider tool call.

## Scope deliberately rejected

- no new top-level skill;
- no universal confirmation dialog for ordinary reads;
- no mandatory multi-agent privilege separation;
- no wildcard permission model;
- no imported third-party authorization runtime.

## Evidence level

This release provides external-pattern audit + deterministic contract validation. It does **not** prove reduced incident rates or universal runtime enforcement. Representative real-task outcome evidence remains required.
