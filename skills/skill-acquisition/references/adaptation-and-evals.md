# Adaptation and Evaluation Gates

External inspiration becomes DEDAL behavior only after an explicit adaptation and evaluation path.

## Adaptation checklist

1. Preserve the problem being solved, not the source skill's branding or runtime assumptions.
2. Keep platform/system instructions above skill instructions.
3. Preserve Creator authority for irreversible, sensitive, production, and canon-changing actions.
4. Prefer live authoritative state over memory or cached summaries.
5. Keep the entrypoint concise; move deep material into references/scripts/assets.
6. Use the smallest matching skill set and avoid global mandatory-invocation rules unless genuinely constitutional.
7. Make execution provider-agnostic when the workflow does not require one vendor.
8. Declare write/destructive behavior, external transmission, persistence, and credential requirements.
9. Require fresh evidence for build/test/deploy/completion claims.
10. Record external influences and inspected revisions when they materially shaped the adaptation.

## Evaluation design

Choose representative tasks from actual DEDAL usage. Compare the current skill against the adapted candidate on outcomes that matter:

- task success/correctness;
- missed constraints or regressions;
- unnecessary questions/ceremony;
- context overhead;
- verification quality;
- security/privacy behavior;
- rollback/recovery behavior;
- portability across currently available tools.

Do not promote based only on prose quality or theoretical completeness.

## Promotion gates

A candidate may become active when:

- the capability gap is real and recurring;
- source/license/provenance review is complete;
- security audit has no blocking finding;
- DEDAL-specific conflicts have been removed;
- evaluation shows improvement or a justified new capability without material regression;
- registry/index/continuity and integrity checks are updated;
- rollback to the previous skill is obvious from Git history.

If evidence is mixed, keep the candidate experimental or adopt only the proven pattern.

## Regression capture

When a newly adopted pattern later fails in real use, capture the failure as the smallest durable artifact that prevents recurrence: test fixture, evaluation prompt, validation rule, reference note, or workflow gate. Avoid growing the Stable Kernel for skill-local lessons.
